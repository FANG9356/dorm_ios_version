# วิสัยทัศน์และทิศทางผลิตภัณฑ์ DormiNetX

อัปเดตล่าสุด: 18 กันยายน 2569

เอกสารนี้สรุปเจตนาของผลิตภัณฑ์จาก requirement และ feedback ที่ใช้พัฒนาโครงการ ไม่ได้อ้างว่าเป็นคำพูดส่วนตัวของผู้สร้างทุกถ้อยคำ หากจะเปลี่ยนหลักการระดับนี้ควรยืนยันกับเจ้าของโครงการก่อน

## เป้าหมายหลัก

DormiNetX ต้องเป็นระบบจัดการหอพักที่ผู้ดูแลใช้ทำงานประจำวันได้จริงบน iPhone/iPad และลูกบ้านได้รับข้อมูลสำคัญผ่าน LINE โดยไม่ต้องเรียนรู้ระบบซับซ้อน ข้อมูลต้องเชื่อถือได้ ตรวจย้อนหลังได้ และไม่สูญหายเพราะสัญญาณอินเทอร์เน็ตหรือการเปลี่ยนอุปกรณ์

ระบบไม่ได้มุ่งเป็นเพียงหน้าจอ CRUD หรือแอปสาธิต แต่ต้องรองรับวงจรจริงของหอพักตั้งแต่ห้อง ลูกบ้าน สัญญา ราคา บิล การรับเงิน หลักฐาน งานซ่อม ไปจนถึง backup และการกู้คืน

## ประสบการณ์ที่ผู้สร้างต้องการ

- **เรียบ พรีเมียม และเป็นธรรมชาติแบบ iOS** — ใช้ material/glass อย่างมีวินัย สีสถานะเป็น accent ไม่ถมพื้นที่มาก และมี visual hierarchy ที่อ่านครั้งเดียวเข้าใจ
- **ลดการกดผิด** — หน้ารายการใช้เพื่อดูและค้นหา การแก้ข้อมูลสำคัญต้องเข้าไปในรายละเอียดก่อน งานลบและการเปลี่ยนสถานะต้องมีการยืนยันหรือข้อจำกัดที่เหมาะสม
- **ข้อมูลมากแล้วต้องยังหาเจอ** — หน้ารายการหลักต้องมีรูปแบบค้นหา/กรองที่สม่ำเสมอ รองรับการแตะและลากโดยไม่แย่ง gesture การเลื่อน
- **ภาษาไทยและวันที่ต้องถูกต้อง** — storage ใหม่ใช้ Gregorian ค.ศ. ส่วน UI ไทยแสดง พ.ศ. อย่างสม่ำเสมอ ห้ามบวก 543 ซ้ำ และเวลาธุรกิจอ้าง `Asia/Bangkok`
- **LINE เป็นช่องทางของลูกบ้าน** — ลูกบ้านควรดูยอด ส่งสลิป แจ้งซ่อม และรับความคืบหน้าได้จาก LINE ส่วนแอปเป็นเครื่องมือหลักของผู้ดูแลและเป็นแหล่งข้อมูลที่ต้อง sync กลับมาเห็นตรงกัน
- **รู้ค่าใช้จ่ายก่อนซ่อม** — งานซ่อมที่มีค่าใช้จ่ายต้องแจ้งยอดและให้ลูกบ้านที่ผูกบัญชีอนุมัติก่อนเริ่มซ่อม ไม่ใช่ซ่อมเสร็จแล้วจึงเรียกเก็บโดยไม่แจ้งล่วงหน้า
- **หนึ่งเหตุการณ์ หนึ่งข้อความที่ชัดเจน** — การตอบรับสำเร็จใน LINE ควรแสดงผลด้วยการ์ดเดียว ไม่ส่งข้อความธรรมดาและ Flex ที่มีความหมายซ้ำกัน ยกเว้นข้อความสำรองเมื่อสร้างหรือเข้าคิวการ์ดไม่ได้จริง
- **ทำงานได้แม้อินเทอร์เน็ตไม่สมบูรณ์** — local-first, retry, idempotency, conflict protection และสถานะที่บอกผู้ใช้ได้ว่าข้อมูลอยู่ในเครื่อง กำลังส่ง หรือส่งไม่สำเร็จ

## หลักการผลิตภัณฑ์ที่ต้องรักษา

1. ความถูกต้องและการกู้คืนข้อมูลมาก่อนความเร็วในการเพิ่มฟีเจอร์
2. ข้อมูลทุกชุดต้องแยกตามบัญชีและ tenant; ห้ามอาศัยเลขห้องอย่างเดียวเป็น identity ระยะยาว
3. การเงินต้องตรวจย้อนหลังได้ ไม่แก้ยอดที่รับเงินจริงแบบไร้ร่องรอย
4. การส่ง LINE ต้องส่งถูกคน ไม่ส่งซ้ำ มี retry และแยกความสำเร็จของการบันทึกข้อมูลออกจากความสำเร็จของ provider
5. การเปลี่ยน workflow สำคัญต้องมี validation ทั้งแอปและ backend ไม่พึ่ง UI อย่างเดียว
6. UI ไม่ควรซ่อน action สำคัญไว้ใน swipe/long-press ที่แย่งการเลื่อนหรือทำให้ค้นพบยาก
7. Production ต้องมี backup, health check และ rollback ที่พิสูจน์แล้ว ไม่ใช่มีเพียง script ที่ยังไม่เคย drill
8. สถานะที่ยุติ workflow เช่น `ปฏิเสธค่าใช้จ่าย` ต้องแสดงตรงกันในแอป, backend, snapshot และ LINE และต้องไม่ถูกตีความเป็นขั้นปกติที่เดินหน้าต่ออัตโนมัติ

## ขอบเขตผู้ใช้เป้าหมาย

- ผู้ดูแลหอพักขนาดเล็กถึงกลางที่ทำงานจาก iPhone/iPad
- ผู้ดูแลหลายคนภายใต้หอเดียวกัน โดยต้องไม่สร้าง tenant ใหม่ผิดขอบเขต
- ลูกบ้านที่ใช้ LINE เป็นช่องทางหลักในการดูข้อมูล ส่งหลักฐาน และตอบรับค่าใช้จ่าย

## ทิศทางระยะถัดไป

ระยะใกล้ต้องเน้นความน่าเชื่อถือของ production ได้แก่ secret rotation, UAT สองเครื่อง/สองบัญชี, media lifecycle, ledger/refund/void และ restore drill ก่อนเพิ่มฟีเจอร์ใหญ่ ระยะถัดไปจึงค่อยเพิ่ม APNs, localization, accessibility, performance และ TestFlight pilot หนึ่งรอบบิลเต็ม

## สิ่งที่ไม่ควรทำ

- อย่าประกาศว่า “พร้อม 100%” จากการ build หรือ unit test เพียงอย่างเดียว
- อย่าทดสอบด้วยการเปลี่ยนข้อมูล production จริงโดยไม่มีเจ้าของข้อมูลและแผนย้อนกลับ
- อย่าให้แอดมินข้ามการอนุมัติค่าซ่อมแบบมีค่าใช้จ่าย
- อย่าส่ง URL สื่อแบบ public หรือให้ tenant อื่นเปิดไฟล์ได้
- อย่าเพิ่มสีและองค์ประกอบตกแต่งจนกลบข้อมูลหลักหรือทำให้แต่ละหน้ามีภาษาภาพคนละชุด
