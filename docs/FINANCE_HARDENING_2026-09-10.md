# ความคืบหน้าระบบการเงิน

วันที่ 10 กันยายน 2569 ต่อจาก [งานระบบหลักวันที่ 9 กันยายน](CORE_HARDENING_2026-09-09.md)

> สรุปสถานะล่าสุดและงานการเงินที่ยังเหลืออยู่ที่ [CURRENT_STATUS_2026-09-16.md](CURRENT_STATUS_2026-09-16.md)

## ขอบเขตรอบนี้

แก้ความถูกต้องของฟอร์ม PaymentEditor ที่ใช้ร่วมกันในหน้าการเงิน บิล และหลักฐานการโอน ยังไม่ใช่การเปลี่ยนเป็น financial ledger เต็มรูปแบบ ส่วน backend hardening ถูก deploy ภายหลังตาม [บันทึก production](PRODUCTION_HARDENING_2026-09-10.md) แต่ iOS ledger ในเอกสารนี้ยังต้องผ่าน device UAT ก่อนแจกจ่ายจริง

> อัปเดต 16 กันยายน 2569: iOS suite ปัจจุบันผ่าน 44/44 และมี device UAT บาง flow บน iPhone จริงหนึ่งเครื่องแล้ว แต่เกณฑ์ production ยังต้องผ่าน UAT สองเครื่อง/สองบัญชี และทำ refund/void/credit adjustment workflow พร้อม audit trail ให้ครบ

### สิ่งที่แก้แล้ว

- เพิ่ม `Payment.depositFee` และส่งผ่าน snapshot/backup; บิลใหม่แบบเต็มจำนวนและจองแยกเงินมัดจำจากค่าเช่า
- บิลเก่าที่ `amount` ไม่เท่ากับผลรวมรายการย่อย จะเก็บส่วนต่างไว้เป็น “ยอดเดิมที่ยังไม่แยกรายการ” ทั้งฟอร์มและใบเสร็จ ไม่เดาว่าเป็นมัดจำหรือส่วนลด และไม่ทิ้งเมื่อแก้รายการอื่น
- ฟอร์มเปิดยอดเดิมด้วยทศนิยม 2 ตำแหน่ง ไม่ปัดสตางค์ทิ้ง; การรวมยอดใช้ Decimal และปัดที่หน่วยสตางค์
- “ชำระแล้ว” ใช้ยอดเต็มบิล, “จ่ายบางส่วน” ต้องมากกว่า 0 และน้อยกว่ายอดบิล, “รอชำระ” ต้องไม่มีเงินรับ ไม่เปลี่ยนสถานะ/ตัดยอดที่กรอกเกินแบบเงียบ ๆ
- ไม่อนุญาตให้ฟอร์มแก้ไขลดยอดรับเงินที่บันทึกไว้แล้ว การคืนเงินหรือย้อนรายการต้องมี workflow ต่างหาก ไม่ใช่เปลี่ยนตัวเลขทับ
- คง `userId` ของบิลเดิมและแสดงชื่อลูกบ้านตาม ID ไม่เปลี่ยนเป็นคนที่เพิ่งเข้าห้องเดิม; คงค่ามิเตอร์เดิมเมื่อแก้รายการจากหน้าการเงิน
- ไม่เปลี่ยนวันที่รับเงินเก่าเพียงเพราะแตะสถานะเดิมซ้ำ
- Callback การบันทึกฟอร์มส่ง error กลับได้ เมื่อ SwiftData save ล้มเหลวจะ rollback และคงฟอร์มไว้พร้อมแจ้งข้อผิดพลาด การซิงก์เริ่มหลังบันทึกในเครื่องสำเร็จ
- เริ่ม ledger แบบเพิ่มข้อมูลโดยไม่ทำลาย schema เดิม: ทุกยอดรับที่เพิ่มขึ้นสร้าง `PaymentTransaction` และ snapshot ข้อเท็จจริงเป็น `FinancialReceipt`; การเปิด store/restore snapshot เก่าจะ migrate ยอดสะสมเดิมแบบ idempotent
- ธุรกรรมและใบเสร็จใหม่รวมอยู่ใน account snapshot และ local backup แล้ว โดย decoder ยังคงรับ snapshot รุ่นเก่าที่ไม่มี ledger ได้
- เมื่อดึง snapshot รุ่นเก่าที่มียอดรับแต่ไม่มี ledger แอปจะสร้าง ledger แบบ idempotent และตั้ง pending sync เพื่อส่ง identifiers ชุดเดียวกลับขึ้น cloud ไม่ mark ประวัติที่เพิ่งสร้างเป็นข้อมูล clean
- ตรวจ referential integrity ของ ledger ก่อน export/push/restore/apply: transaction ต้องอ้างบิลที่มีอยู่และมีใบเสร็จคู่กันหนึ่งรายการ ยอดรับต้องตรงกัน และเลขใบเสร็จต้องไม่ซ้ำ; backup ที่ทำให้ ledger เป็น orphan จะถูกปฏิเสธก่อนลบข้อมูลในเครื่อง
- ไม่อนุญาตให้ลบบิลที่มีประวัติรับเงินแล้ว เพราะจะทำให้ธุรกรรม/ใบเสร็จกลายเป็น orphan; ต้องรอ workflow คืนเงินหรือปรับยอด ส่วนบิลที่ยังไม่เคยรับเงินยังลบได้
- ครอบ mutation, การสร้าง ledger และ `modelContext.save()` ใน rollback boundary เดียวกันทุก PaymentEditor ที่เชื่อมแล้ว เพื่อไม่ให้ค่าที่ ledger ปฏิเสธค้างอยู่ใน context และถูกบันทึกภายหลัง

ตัวอย่าง regression ที่แก้: ค่าเช่า 1,500.25 + ส่วนต่างเดิม 75 = 1,575.25 บาท เมื่อเปิดแล้วบันทึกฟอร์ม ยอดยังเป็น 1,575.25 ไม่กลายเป็น 1,500 บาท

## การทดสอบ

- `PaymentAmountsTests` 5 กรณี: สตางค์, ส่วนต่างบิลเก่า, มัดจำไม่ซ้ำ, สถานะขัดกับยอด และการลดยอดรับเดิม
- เพิ่ม backup round-trip พร้อมกู้คืน snapshot เก่าที่ไม่มี `depositFee`
- `PaymentStoreMigrationTests` สร้าง SQLite ชั่วคราวด้วย schema Payment ก่อนเพิ่มมัดจำ แล้วเปิดด้วย schema ปัจจุบัน ยืนยัน UUID ยอดรวม ยอดรับ และชื่อไฟล์สลิปอยู่ครบ
- `PaymentLedgerTests` ตรวจรับเงินหลายครั้งเป็นคนละ transaction, receipt facts ไม่เปลี่ยนตามบิล, migration ไม่สร้างซ้ำ, ห้ามลดยอดรับเดิม และห้ามลบบิลที่มีประวัติรับเงิน
- iOS suite รวม 42 กรณี ผ่านรอบสุดท้ายหลังเพิ่ม ledger integrity และ delete guard รายละเอียดผลอยู่ด้านล่าง
- การทดสอบนี้ไม่ใช่การอัปเกรดฐานข้อมูล production และไม่ได้พิสูจน์ว่าไฟล์รูปที่อ้างถึงเปิดได้ข้ามเครื่อง

## ข้อจำกัดที่ยังต้องทำ

1. ทำ migration จาก `Payment` ไปเป็น Invoice เต็มรูปแบบ และเปลี่ยนหน้าดู/ส่งออกใบเสร็จให้ใช้ `FinancialReceipt` ที่บันทึกไว้แทนการ render จาก `Payment` ที่ยังแก้ไขได้ ปัจจุบันเริ่มแยก `PaymentTransaction`/`FinancialReceipt` แล้ว แต่ `Payment.paidAmount` ยังเป็น compatibility balance
2. แยกส่วนมัดจำในแผนผ่อนที่มีอยู่แล้ว และกำหนดการกระจายมัดจำแต่ละงวดโดยมี migration ที่ตรวจสอบได้ รอบนี้ยังไม่จัดประเภทเงินในบิลเก่าใหม่ให้เอง
3. ตรวจกรณีจองแล้วเข้าอยู่จริงว่ามีบิลค่าเช่าแรกครบ โดยไม่คิดเงินจอง/มัดจำซ้ำ รวมถึงการแก้สัญญาหลังมีแผนผ่อน
4. Workflow ยกเลิก/คืนเงิน/ลดหนี้พร้อมเหตุผลและ audit trail; ปุ่มลบ/อนุมัติ/ปฏิเสธนอกฟอร์มยังต้องรวมอยู่ใน ledger เดียวกัน
5. ทดสอบ UI กดจริง, save failure/พื้นที่เต็ม, บัญชีหลายเครื่อง และข้อมูลเก่าที่ไม่สะอาด ก่อนปล่อยรุ่น

สำรองข้อมูลก่อนอัปเดต และอัปเดตทุกเครื่องร่วมกันตามข้อกำหนด sync protocol ในรายงานวันที่ 9 กันยายน แอปรุ่นเก่าไม่รู้จัก `depositFee` และฟอร์มรุ่นเก่ายังมีบั๊กทิ้งส่วนต่าง แม้ยอดรวมใน snapshot จะยังอยู่

## ประเมินความพร้อม

ระบบหลักประมาณ 75–80% เหลืองานประมาณ 20–25% เป็นประมาณการจากขอบเขตงานและความเสี่ยง ไม่ใช่สัดส่วน test coverage และไม่รวม LINE/หลายภาษาที่เลื่อนออกไป ยังไม่เพิ่มคะแนนเพราะ test ผ่านอย่างเดียว

งานที่ค้างมีความเสี่ยงสูง: ledger/migration, สื่อและ backup ข้ามเครื่อง, authorization/session revocation และ end-to-end บนอุปกรณ์จริง ต้องผ่านก่อนเรียก production-ready
